# M10: replay harness and acceptance runs

**Purpose:** make the acceptance scenarios reproducible without flying anything,
by publishing recorded traces through the same measurement store the sensor uses.

**Date:** 2026-10-30
**Build:** 66 600 B flash / 25 344 B RAM (replay image)

## 1. How it works

```
LIVE    BMP280 ──► sensor thread ──┐
                                   ├──► SensorDataStore ──► altitude ──► apogee ──► LED
REPLAY  traces/ ──► replay thread ─┘                          └──► heat ────────────┘
```

- The trace player publishes a `Measurement` every 50 ms with the **uptime**
  timestamp, so the 750 ms window and the 10 s indication are real time.
- Exactly one publisher exists per boot: in replay mode the sensor thread is
  never created, and the I²C recovery is skipped.
- A trace ends by publishing an invalid snapshot, so consumers cannot treat the
  end of a replay as live data.
- The boot banner is explicit:

```
TEST MODE: REPLAY at05 (live sensor not used)
input: REPLAY at05, 50 ms cadence (live sensor not used)
threads: replay(5) altitude(6) apogee(7) heat(8) led(9) telemetry(10)
```

## 2. Traces

Generated by `tools/make-traces.py` from height profiles, converted with
`P = P0 · (1 − h/44330)^(1/0.1903)`, `P0 = 95 120 Pa`. Both the CSV (human
readable) and `src/traces_data.hpp` (embedded) are committed.

| Trace | Profile | Expected |
|---|---|---|
| `at04a` | descend to −1.2 m | no deployment |
| `at04b` | climb to 4 m and hold | no deployment |
| `at05` | baseline, climb to 6 m, peak, descend at 2 m/s | one deployment ~0.6 s after the peak |
| `at08` | at05 + heat 7.3–11.0 s | ON → blink → ON until the deadline |
| `at09` | at05 + heat 17.5-22.5 s | blink after the deadline; no steady ON afterwards |
| `at07a` | flat, heat 4.0-9.0 s | blink 5 s, then off; no deployment |
| `at07b` | flat, heat 4.0-14.0 s | two renewals, then cooling clears it |

23 host checks (`tests/trace_test.cpp`) verify the embedded data: timestamps
increase, pressures are within the sensor's range, every trace starts with a 2 s
baseline, and `at05` really reaches ~6 m.

## 3. Acceptance results

Each run: build, flash, attach RTT, no breakpoints, continuous. Timing tolerance
on the LED is the 10 ms update period plus logging, so 5.000 s and 10.000 s are
quoted to the millisecond the transition was recorded.

### AT-04a — descending but below the minimum

```
deploys: 0
apogee: h=-1.15 m  v=-0.075 m/s  cov=1550 ms  state=ready
```

### AT-04b — above the minimum but not descending

```
deploys: 0
apogee: h=3.99 m  v=0.000 m/s  cov=1550 ms  state=ready
```

### AT-05b - literal thresholds

Same trace, built with `MIN_DESCENT_MM_S=0` and `MIN_DROP_CM=0`, i.e. the
assignment's rule with no added guards:

```
REPLAY TEST: at05
apogee: DEPLOY at 5.50 m, v=-0.167 m/s; LED on until 15561 ms
led:  [      5.561] on (deployment)
led:  [     15.561] off
```

One event, 10.000 s of steady light. The shipped default (0.3 m/s margin, 25 cm
drop) triggers slightly later, at 5.41 m and v=-0.495 m/s; both are correct, and
the strict one exists to stop air drift from firing it.

### AT-05 / AT-06 - one deployment, 10 s, no retrigger

```
apogee: DEPLOY at 5.41 m, v=-0.495 m/s; LED on until 15611 ms (seq=113)
led:  [      5.611] on (deployment)
led:  [     15.611] off
REPLAY TEST: done, 381 samples published
```

- One deployment, at 5.41 m — 0.61 s after the 6 m peak.
- LED on for **exactly 10.000 s**.
- Continued descent (−9 m) produced no second event.

### AT-07a — heat only, one 5 s window

```
TEST MODE: REPLAY at07a (live sensor not used)
heat: HOT at 32.000 C; alarm until 9011 ms (seq=81)
led:  [      4.011] blink on (heat)
led:  [      4.261] blink off (heat)
…
led:  [      9.011] off
heat: cooled at 24.000 C; alarm cleared
```

Blink from 4.011 to 9.011 = **exactly 5.000 s**, 250 ms half-period, and **no
deployment** anywhere in the run (altitude stays at 0, so the apogee detector
never arms a drop).

### AT-07b — heat across renewals, then cooling

```
heat: HOT at 32.000 C; alarm until 9011 ms
heat: HOT at 32.000 C; alarm until 14011 ms   ← renewal 1
heat: HOT at 32.000 C; alarm until 19011 ms   ← renewal 2
heat: cooled at 24.000 C; alarm cleared
led:  [     14.011] off
```

Blink ran 4.011 → 14.011 (10 s) with two 5 s renewals and no gap, then cooling
cleared it immediately. There is no deployment to fall back to, so the output is
off, not steady ON.

### AT-08 — heat during deployment, cooling before the deadline

```
apogee: DEPLOY … LED on until 15611 ms
led:  [      5.611] on (deployment)
led:  [      7.311] blink on (heat)      ← heat starts 1.7 s after deployment
heat: cooled at 24.000 C; alarm cleared (seq=221)
led:  [     11.011] on (deployment)      ← steady resumes
led:  [     15.611] off                  ← original deadline, not extended
```

Steady ON 5.6–7.3 s, blink 7.3–11.0 s, steady ON again 11.0–15.6 s (4.6 s, the
remaining part of the original window), then off.

### AT-09 — heat after the deployment deadline

```
led:  [      5.611] on (deployment)
led:  [     15.611] off                  ← deployment expired
heat: HOT at 32.000 C; alarm until 22511 ms
led:  [     22.511] off                  ← cooling after the deadline: no steady ON
```

### AT-11 — new flight after a reset

Each of the five runs above followed a reset/flash. `at05` deployed exactly once
per reset, and a fresh baseline and history were rebuilt every time. The reset
procedure is a power cycle; there is no button or command.

## 4. Diffuse scenarios not covered

- **Hand-flown behaviour.** Replay proves logic and timing, not sensor physics.
  Live acquisition is proven separately (AT-02/03).
- **AT-10 consolidated report.** Consumers ran together in every run, but the
  sequence comparison is not tabulated here; it is in `m5-shared-memory.md`.
- **A true "flight reset" control.** AT-11 is satisfied by resetting the board,
  not by an in-flight re-arm.

## 5. Reproducing

```powershell
west build -p always -b olimex_stm32_h407 -d build/replay . -- `
  "-DCONFIG_APP_REPLAY=y" "-DCONFIG_APP_TRACE_AT05=y"
tools\rtt-session.ps1 -Flash -BuildDir build\replay
```

Trace selection is a Kconfig choice (booleans), so each scenario is a build and
its evidence is tied to that binary.
