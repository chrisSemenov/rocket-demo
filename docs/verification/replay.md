# M10: replay harness and acceptance runs

**Purpose:** make the acceptance scenarios reproducible without flying anything,
by publishing recorded traces through the same measurement store the sensor uses.

**Date:** 2026-10-31
**Commit:** `db3531c`
**Build:** 74 248 B flash / 24 128 B RAM (replay image at `db3531c`); 74 256 B
for the literal-threshold build. The 2026-11-01 `at05` re-run with the peak
estimate is 75 124 B (`build/at05peak`).
**Raw captures:** `tests/evidence/m10/*.log`

## 1. How it works

```
LIVE    BMP280 --> sensor thread --+
                                   +--> SensorDataStore --> altitude --> apogee --> LED
REPLAY  traces/ --> replay thread -+                       \--> heat ------------+
```

- The trace player publishes a `Measurement` for each trace sample, timestamped
  with the **current uptime**, so the 750 ms window and the 10 s indication run in
  real time rather than trace time.
- The pacing comes from the trace's own timestamps (`t[i+1] - t[i]`), not from an
  assumed 50 ms. A trace with irregular spacing plays at its recorded spacing.
- Exactly one publisher exists per boot: in replay mode the sensor thread is
  never created and the boot bus recovery is compiled out.
- A trace ends by publishing an invalid snapshot, so consumers cannot treat the
  end of a replay as live data.
- The boot banner is explicit:

```
TEST MODE: REPLAY at05 (live sensor not used)
input: REPLAY at05, 50 ms cadence (live sensor not used)
threads: replay(5) altitude(6) apogee(7) heat(8) led(9) telemetry(10)
```

## 2. Traces

Generated by `tools/make-traces.py` from height profiles, converted with
`P = P0 * (1 - h/44330) ^ (1/0.1903)`, `P0 = 95 120 Pa`. Both the CSV (readable)
and `src/traces_data.hpp` (embedded) are committed, and
`tools/check-traces.ps1` fails if they drift from the generator.

| Trace | Profile | Expected |
|---|---|---|
| `at04a` | descend to -1.2 m | no deployment (below the minimum) |
| `at04b` | climb to 4 m and hold | no deployment (not descending) |
| `at05` | baseline, climb to 6 m, peak, descend at 2 m/s, end at -17.4 m | one deployment, then 19 s with no retrigger |
| `at05b` | same as `at05`, built with zero margin and zero drop | one earlier deployment, proving the literal rule |
| `at08` | at05 + heat 8.0-13.0 s | ON, blink, ON for the remainder, OFF at the deadline |
| `at09` | at05 + heat 12.0-17.0 s | blink spans the 15.6 s deadline; cooling afterwards gives OFF |
| `at07a` | flat, heat 4.0-9.0 s | blink 5 s, then off; no deployment |
| `at07b` | flat, heat 4.0-14.0 s | renewals, then cooling clears it |

24 host checks (`tests/trace_test.cpp`) verify the generated data: timestamps
increase, pressures are in range, every trace is stationary for its first 2 s,
`at05` reaches about 6 m, and `at05` runs at least 15 s past the deployment.

A further 34 checks (`tests/replay_sim_test.cpp`) run the **real** altitude,
detector, heat and LED units over the **real** traces on the PC. That is not
on-target evidence, but it means every expected outcome below was known before
the board was flashed, and a regression in the traces or the policies shows up
without hardware.

## 3. Acceptance results

Each run: build, flash, attach RTT, no breakpoints, run continuously. LED
timings are the transition log at 10 ms resolution, so a 10.000 s indication
means exactly that within one update period.

### AT-04a - descending but below the minimum

```
apogee: h=-1.15 m  v=-0.120  slope=-0.146  cov=1550 ms  n=32  state=ready  seq=158
```

Zero `DEPLOY` lines. The velocity really is negative; the altitude gate is what
stops it.

### AT-04b - above the minimum but not descending

```
apogee: h=3.99 m  v=0.000  slope=0.000  cov=1550 ms  n=32  state=ready  seq=178
```

Zero `DEPLOY` lines.

### AT-05 / AT-06 - one deployment, 10 s, no retrigger

```
apogee: DEPLOY at 5.41 m, v=-0.360 m/s (slope=-0.495); LED on until 15611 ms (seq=113)
led:  [      5.611] on (deployment)
led:  [     15.611] off
REPLAY TEST: done, 501 samples published
```

Re-run on 2026-11-01 with the peak estimate, same sample:

```
apogee: DEPLOY at 5.41 m, v=-0.360 m/s (slope=-0.495); estimated apogee 6.03 m
        at 5.01 s (drop 62 cm, delay 0.60 s); LED on until 15611 ms (seq=113)
```

- One deployment, at 5.41 m, 62 cm below the estimated apogee, 0.60 s after it.
  (The trace holds 6.03 m from 5.00 to 5.30 s; the estimate is timestamped at the
  start of that plateau, while an earlier version quoted 0.41 s from its middle.)
- LED on for exactly 10.000 s.
- Then 19.4 s of further descent to -17.28 m with no second event and no change
  to the deadline.

### AT-05b - the literal rule

Built with `CONFIG_APP_APOGEE_MIN_DESCENT_MM_S=0` and
`CONFIG_APP_APOGEE_MIN_DROP_CM=0`:

```
apogee: armed; threshold 150 cm, drop 0 cm, margin 0 mm/s
apogee: DEPLOY at 5.50 m, v=-0.120 m/s (slope=-0.167); LED on until 15561 ms (seq=112)
led:  [      5.561] on (deployment)
led:  [     15.561] off
```

One event, 10.000 s. The shipped defaults move the trigger from 5.50 m to
5.41 m on the same trace; both are correct, and the defaults exist because a
stationary sensor satisfies "negative" on pressure noise.

### AT-07a - heat only, one 5 s window

```
heat: HOT at 32.000 C; alarm until 9011 ms (seq=81)
led:  [      4.011] blink on (heat)
led:  [      4.261] blink off (heat)
...
led:  [      9.011] off
heat: cooled at 24.000 C; alarm cleared (seq=181)
```

Blink from 4.011 to 9.011 = exactly 5.000 s at 250 ms half-periods, and no
deployment anywhere in the run.

### AT-07b - heat across renewals, then cooling

```
heat: HOT at 32.000 C; alarm until 9011 ms (seq=81)
heat: still hot at 32.000 C; alarm extended to 14011 ms (seq=180)
heat: still hot at 32.000 C; alarm extended to 19011 ms (seq=280)
heat: cooled at 24.000 C; alarm cleared (seq=281)
led:  [     14.011] off
```

Blink ran 4.011 to 14.011 with no gap at either renewal, then cooling cleared it
immediately. With no deployment to fall back to, the output is off.

### AT-08 - heat during deployment, cooling before the deadline

```
apogee: DEPLOY at 5.41 m ... LED on until 15611 ms
heat: HOT at 32.000 C; alarm until 13011 ms (seq=161)
heat: still hot at 32.000 C; alarm extended to 18011 ms (seq=260)
heat: cooled at 24.000 C; alarm cleared (seq=261)
led:  [      5.611] on (deployment)
led:  [      8.011] blink on (heat)
led:  [     13.011] on (deployment)
led:  [     15.611] off
```

ON for 2.400 s, blink for 5.000 s, ON for the remaining 2.600 s of the original
window, then off. The renewal at 12.95 s never ran: the cooling sample arrived
60 ms later and cleared it.

### AT-09 - overheating across the deadline

```
heat: HOT at 32.000 C; alarm until 17011 ms (seq=241)
led:  [      5.611] on (deployment)
led:  [     15.011] blink on (heat)
led:  [     15.261] blink off (heat)
led:  [     15.511] blink on (heat)
led:  [     15.761] blink off (heat)      <- past the 15611 ms deadline
heat: cooled at 24.000 C; alarm cleared (seq=341)
led:  [     17.011] off
```

There is no `off` transition anywhere between 12 s and 16.9 s: the blink owned
the LED across the whole deployment window and beyond it. Cooling at 17.011 s
gives OFF, not steady ON, because the original deadline had passed.

### AT-11 - new flight after a reset

Both runs used the same flashed image; the second followed a reflash (the
documented reset procedure is a power cycle or reflash -- there is no button or
command).

```
run 1: alt: baseline frozen P0=95120 Pa after 38 samples (spread 0 Pa)
       apogee: DEPLOY ... LED on until 15611 ms (seq=113)
run 2: alt: baseline frozen P0=95120 Pa after 38 samples (spread 0 Pa)
       apogee: DEPLOY ... LED on until 15611 ms (seq=113)
```

Fresh calibration and history each time, exactly one deployment each time.

## 4. What this does not cover

- **Hand-flown behaviour.** Replay proves logic and timing, not sensor physics.
  Live acquisition is proven separately (AT-02/AT-03).
- **A true in-flight re-arm.** AT-11 is satisfied by resetting the board.
- **A physical heat event.** AT-07 uses a replayed temperature.
